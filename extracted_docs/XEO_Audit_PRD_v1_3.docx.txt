1. Product definition
Goal. Given one public website URL and a selected search/performance device context, automatically analyze the site and produce an evidence-based XEO assessment covering Search, AI-generated discovery and language-model readiness/performance, understandable by both a technical operator and a business client.
The V1 is intentionally a compact audit product, not a replacement for enterprise SEO suites. It must favor explainability, conservative crawling and professional reporting over breadth of features.
1.1 Product outcomes
Identify whether the site can be crawled and appears technically eligible for indexing.
Measure on-page SEO quality, site architecture, structured data and basic image hygiene.
Measure real-user Core Web Vitals when CrUX data exists; otherwise fall back to Lighthouse laboratory testing and state this explicitly.
Assess AIgen & LM Readiness through observable AEO/GEO signals plus clearly labeled LLM-assisted semantic analysis.
Generate a small, defensible keyword universe, validate it with external search data, select ten representative keywords, observe the domain’s Google positions for the selected device, and use those observed positions in Keyword Position Performance.
Produce prioritized issues and remediation actions without claiming to reproduce Google ranking algorithms or guarantee AI citations.
1.2 V1 success condition
One URL in → one complete audit out, with graceful degradation when one external data source is unavailable.
2. Inputs and automatic context detection
2.1 Mandatory user input
V1 exposes two run inputs: a public website URL and a device selector with allowed values Mobile or Desktop. URL is mandatory. Device defaults to Mobile when not explicitly changed by the operator.
The selected device is a run-level parameter. It MUST be propagated consistently to DataForSEO Google SERP, CrUX form-factor selection where available, PageSpeed/Lighthouse strategy and report metadata. The target-site HTML crawl remains standard HTTP and MUST NOT be described as full browser/device emulation.
2.2 Context inferred by the system
Canonical host/domain and preferred scheme (HTTP/HTTPS normalization).
Primary website language.
Business/entity type and main products/services.
Probable geographic market from TLD, addresses, LocalBusiness/Organization data, contact pages and visible content.
Commercial and informational themes required for keyword and AEO/GEO analysis.
Requirement: the report must disclose the inferred language and geographic market. If confidence is weak, the tool must label the assumption rather than silently treating it as certain.

4.3 Representative page selection
V1 is a representative website audit crawler, not a full-site spider. Discovery may inspect robots.txt, sitemap files and internal-link relationships. Public, same-host, crawlable HTML pages that pass deterministic safety exclusions form the candidate pool. Page-type labels support representative sampling and later analysis, but URL taxonomy alone is not an eligibility gate.
Page class
V1 rule
Selection logic
Homepage
INCLUDE
Always include the normalized public homepage when reachable and not blocked.
Editorial / content
INCLUDE
Blog posts, guides, news, FAQs, knowledge or analogous public content. Sample across topics and templates.
Commercial
INCLUDE
Public product, product-category, service and landing pages. Sample representative offers/templates rather than exhaustive catalogues.
Sensitive / operational
EXCLUDE
Account, login, checkout, cart, payment, admin, private API, form endpoint, user profile, authenticated or action-triggering URLs.
Unclassified public HTML
INCLUDE AS CANDIDATE
Public, same-host, robots-allowed HTML whose role cannot be inferred reliably from the URL remains eligible for representative sampling. Classification may be refined after fetch from normalized PageData evidence; unknown URL taxonomy alone is not an exclusion reason.
Utility / low-value
DEPRIORITIZE
Legal boilerplate, repetitive utility pages and analogous low-value resources should normally be omitted from the capped sample when more informative pages are available. They are not excluded solely because their URL path is unfamiliar.
Sampling rule. The page target is not filled arbitrarily and the crawler never attempts to reconstruct a large catalogue or content database. When the candidate pool exceeds the V1 hard cap, selection must favor a representative mix of distinct templates, topics and site roles, while deprioritizing repetitive, utility or low-value pages when more informative pages are available. When at least 25 safe, analysis-relevant HTML pages are available, the audit should analyze no fewer than 25.
4.4 Crawl, Privacy & Legal Safety Policy
This section defines conservative product-engineering safeguards for auditing third-party websites. It is a risk-control baseline, not legal advice, and does not replace case-specific review where contractual, copyright, database-right or privacy issues are material.
Requirement
V1 policy
Public content only
Analyze only resources accessible without authentication. Never attempt to enter private, restricted or permission-controlled areas.
No protection circumvention
No CAPTCHA bypass, paywall bypass, anti-bot evasion, credential use, proxy rotation intended to defeat restrictions, or circumvention of technical access controls.
Robots respect
Treat robots.txt as a mandatory conservative crawl constraint for V1. Do not crawl URLs disallowed for the configured crawler.
Data minimisation
Collect and retain only information necessary for SEO/AEO/GEO/performance analysis. Avoid harvesting personal data even when visible on a public page.
No personal-data harvesting
Do not build datasets of customer names, personal emails, personal phone numbers, reviews, profiles, payment data or form submissions. Prefer boolean/presence signals where sufficient.
LLM sanitisation
Before sending page content to an LLM, remove scripts/forms and unnecessary personal identifiers; transmit the minimum text and structured evidence required for semantic analysis.
No content replication
Do not archive or reproduce entire third-party articles, catalogues or image libraries in outputs. Store derived metrics, short evidence fragments when necessary, and source URLs.
No substantial database extraction
Use representative sampling for large catalogues/directories. V1 must not systematically reconstruct a third-party product or content database.
Conservative request rate
Use serial requests, polite delays, timeouts and limited retries. Stop or back off on 429; treat repeated 403/5xx or blocking signals as a reason to reduce or terminate crawl activity.
Binary/media restraint
Do not download images, video, documents or other large binary assets unless a later approved requirement explicitly needs them; inspect HTML attributes/URLs instead.
Retention
Retain only audit evidence and derived metrics needed for the report/debugging policy. Raw page bodies should not become a permanent third-party content archive.
Legal-design basis. The GDPR requires purpose limitation, data minimisation and data protection by design/default for personal-data processing. EU copyright rules provide a text-and-data-mining framework for lawfully accessible works subject to rights reservations; V1 therefore minimizes copying and does not treat public availability as unrestricted reuse. Access-control circumvention is outside product scope.

7. Web Performance and Core Web Vitals
Performance must be reported using two different evidence layers, with no ambiguity between real-user and laboratory measurements.
7.1 Real-user layer — Chrome UX Report (CrUX)
Device rule. Query the device-relevant CrUX form factor when the provider exposes it. The selected audit device must remain traceable in PerformanceData and the report.
Query CrUX for the audited origin and, when available, representative URLs.
Capture LCP, INP and CLS distributions / p75 indicators returned by the API.
Record whether data is URL-level or origin-level.
If CrUX has insufficient data, do not infer or fabricate field metrics.
7.2 Laboratory layer — PageSpeed Insights / Lighthouse
Device rule. Run PageSpeed/Lighthouse with the selected Mobile or Desktop strategy. Do not silently switch device during the same audit.
Run PageSpeed/Lighthouse on a small representative page sample rather than every crawled URL.
Default sample: homepage plus up to three representative pages (commercial/service, content, conversion/contact where available).
Capture Performance score and relevant diagnostic metrics/opportunities returned by Lighthouse.
Keep Lighthouse SEO, Accessibility and Best Practices separate from the tool’s own Search Readiness score.
7.3 Mandatory report wording
Core Web Vitals — Real user data available
Core Web Vitals — insufficient real-user data; Lab Performance based on Lighthouse laboratory testing
When applicable, also disclose: “URL-level data unavailable — origin-level CrUX data used.”
7.4 XEO Core Web Vitals bands
When CrUX real-user data are available, XEO maps LCP, INP and CLS into four client-facing bands: TOP = LCP ≤ 2.0 s, INP ≤ 150 ms, CLS ≤ 0.05; GOOD = all metrics within Google Good thresholds (LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.10); AVERAGE = no metric is Poor but at least one is outside Good (up to LCP 4.0 s, INP 500 ms, CLS 0.25); LOW = at least one metric exceeds the Poor boundary. The overall CWV band is the worst of the three metric bands.
TOP is an internal XEO excellence band, not an official Google classification. Google’s underlying Good / Needs Improvement / Poor thresholds remain the reference. If CrUX is unavailable, do not assign a real-user CWV band; show Lighthouse Lab Performance separately.
8. LLM-assisted semantic analysis
The language model is a semantic reasoning component, not a source of technical truth. Deterministic measurements must remain deterministic.
LLM use
Allowed role
Business context

Keyword candidates

Intent & clustering

AIgen & LM Readiness

Recommendations

9. Keyword Intelligence and Keyword Position Performance
Keyword selection must combine semantic understanding with market evidence. The final ten keywords are not selected by the LLM alone.
A  Crawl evidence → extract entity, services, products, location and themes.
B  LLM → generate approximately 30–50 candidate keywords across distinct intents/clusters.
C  DataForSEO Google Ads Keywords Data → retrieve search volume, monthly searches, competition and related metrics for candidates.
D  Filter/rank candidates deterministically using relevance, intent, demand, geographic fit and diversity.
E  Select ten representative keywords for the audit; keep the brand keyword separate from performance scoring.
F  DataForSEO Google SERP → query localized LIVE SERPs using the selected Mobile/Desktop device and detect the audited domain’s observed organic position and ranking URL.
9.1 SERP position requirement
The tool must store both DataForSEO ranking fields when available: rank_group (position within the same result type) and rank_absolute (position across SERP elements). The client-facing table must primarily display the organic group position, together with keyword, landing URL, timestamp, location, language and selected device.
Terminology: use “Observed Google organic position”. Do not present the result as a universal or personalized Google ranking.
9.2 Keyword Position Performance score
For each of the ten selected non-brand keywords: positions 1–3 = 100 points; 4–10 = 80; 11–20 = 60; 21–50 = 30; 51–100 = 10; not found in the observed SERP depth = 0. Keyword Position Performance is the arithmetic mean of the ten keyword scores. The report must still show the actual position table; the score is only the summary layer.
Brand queries are observed separately and MUST NOT inflate Keyword Position Performance.
10. AEO — Answer Readiness
AEO in V1 is an explainable content-readiness analysis. It must not be presented as a proprietary search-engine score.
Identify the ten most relevant user questions derived from products, services and search intent.
Map each question to the best matching page, if any.
Assess whether the page provides a direct answer, supporting explanation, definitions, comparisons, steps, requirements or limitations as appropriate.
Flag uncovered or weakly answered questions as content opportunities.
Preserve the evidence page/section used for every semantic judgment.

15. Failure handling and mandatory fallbacks
Condition
Required behavior
CrUX has no data
Continue with Lighthouse; show “insufficient real-user data” and Lab Performance wording. Do not fabricate a real-user CWV band.
URL-level CrUX unavailable
Use origin-level CrUX if available and label it explicitly.
PageSpeed/Lighthouse API error
Continue technical/semantic audit; Performance section marked unavailable/partial.
LLM API error
Continue deterministic SEO/performance audit; semantic, keyword-generation and AEO/GEO sections marked unavailable.
DataForSEO keyword endpoint error
Do not fabricate search demand; keyword intelligence and downstream position performance are marked partial or unavailable.
DataForSEO SERP endpoint error
Do not infer ranking; Keyword Position Performance is unavailable/partial and the XEO Score must be labeled incomplete rather than silently reweighted.
Crawl partially blocked
Report coverage confidence and base conclusions only on observed pages.
Individual page failure
Log and continue; do not terminate site-level audit.
16. Non-functional requirements
Explainability. Every score and recommendation must be traceable to explicit rules and evidence.
Determinism. Technical facts must not depend on LLM judgment where direct measurement is possible.
Conservative external crawling. No Google SERP scraping, anti-bot bypass, proxy rotation or high-frequency crawl behavior.
Secret management. API keys must never be stored in source files, logs, reports or repositories.
Reproducibility. Audit timestamp, URL, selected device, provider/context parameters and scoring-version identifiers must be stored.
Graceful degradation. Failure of one provider must not invalidate unrelated sections.
Maintainability. Provider-specific code must be replaceable without changing scoring/report semantics.
Privacy & data minimisation. Do not collect or retain personal data not required for the audit; sanitize LLM payloads and prefer presence/derived signals over storing personal identifiers.
Small-product constraint. V1 must remain suitable for a local CLI/desktop execution before SaaS productization.
17. Explicit exclusions from V1
Backlink analysis and third-party authority scores.
Google Search Console and Google Analytics integrations.
Bing Webmaster / Bing AI data.
Social media, reviews and advertising intelligence.
Automated article/content generation.
Automated CMS publishing or site modification.
Continuous rank tracking or historical monitoring.
Database-backed user accounts, billing, credits or team workspaces.
Large-scale crawling of tens of thousands of URLs.
JavaScript browser automation as the default crawler in V1.
Direct scraping of Google search-result pages.
Systematic extraction or reconstruction of third-party catalogues, directories or databases.
Collection of customer/user personal data, reviews or authenticated/private content.
18. V1 acceptance criteria
ID
Acceptance criterion
AC-01
A valid public URL can start an audit; the CLI/UI exposes Mobile/Desktop device selection and defaults to Mobile if no explicit choice is supplied.
AC-02
The tool selects a representative, deduplicated sample with a target/hard cap of 50 safe, analysis-relevant HTML pages, analyzes at least 25 when that many are available, and records coverage. Unknown URL taxonomy alone must not cause the sample to fall below the desired minimum.
AC-03
Technical Eligibility returns PASS / WARNING / CRITICAL with page-level evidence.
AC-04
Search Readiness produces rule-level PASS/WARN/FAIL/N/A evidence without claiming ranking probability.
AC-05
CrUX real-user data are shown when available for the selected device/form factor; absence triggers the approved Lighthouse lab-only wording without a fabricated field-data band.
AC-06
Lighthouse/PageSpeed analyzes a representative page sample using the selected Mobile/Desktop strategy and returns diagnostics separately from Search Readiness.
AC-07
LLM semantic analysis is traceable to crawled evidence and cannot override deterministic technical facts.
AC-08
The keyword pipeline generates candidates, validates them with market data, selects ten representative terms and records selection context.
AC-09
SERP analysis returns observed organic rank and ranking URL for each selected keyword using the selected device, and the report displays all ten keyword positions in a table.
AC-10
AEO maps relevant questions to website answers or identifies coverage gaps.
AC-11
AIgen & LM Readiness reports technical access, entity clarity, evidence and answerability without citation-probability claims.
AC-12
Any unavailable source is explicitly marked; the tool never substitutes invented values.
AC-13
The completed audit is emitted as a structured payload suitable for the separate report generator specification.
AC-14
No API secret or credential is written to source code, output reports or logs.
AC-15
The content-analysis sample contains public, same-host, crawlable, analysis-relevant HTML pages. Restricted, authenticated, transactional, action-triggering, personal-data-oriented and robots-disallowed resources are excluded. Page-type classification supports representative sampling but URL-token matching alone is not an eligibility gate.
AC-16
Restricted, authenticated, transactional, action-triggering, personal-data-oriented and robots-disallowed URLs are excluded from content crawling.
AC-17
LLM-bound content is sanitized/minimized; the audit does not create a persistent archive of raw third-party page bodies, personal data or downloaded media.
AC-18
The crawler uses conservative serial request behavior with delays, limited retries and explicit backoff/stop behavior for rate limiting or blocking signals.
AC-19
XEO Score is calculated from the approved four-pillar weights: Search 40%, AIgen & LM 25%, Web Performance 15%, Keyword Position Performance 20%; Technical Eligibility CRITICAL caps the score at 49/100.

XEO Score uses LOW 0–59, AVERAGE 60–74, GOOD 75–89 and TOP 90–100; TOP requires Technical Eligibility PASS.
AC-21
When CrUX field data exist, Core Web Vitals are mapped to XEO LOW / AVERAGE / GOOD / TOP using the approved thresholds and worst-metric rule; TOP is labeled as an internal XEO band.
AC-22
Keyword Position Performance uses the approved position bands and excludes brand queries from the composite performance score.
